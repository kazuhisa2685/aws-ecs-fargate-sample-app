# 0006. ALB ヘルスチェックの正しいターゲット設定

- **Status**: 採用 (Accepted)
- **Date**: 2026-09-08
- **Related Issues**: [#6](https://github.com/kazuhisa2685/aws-ecs-fargate-sample-app/issues/6)

## Context (背景)

ECS サービスのタスクが `Task failed ELB health checks` で繰り返し停止・再起動される事象が発生した。ALB のヘルスチェックが失敗し続け、タスクが正常にトラフィックを受けられない状態。

アプリは Streamlit(フロントエンド, ポート 8000 または 8001)と FastAPI(バックエンド)の 2 コンテナ構成で、ALB のターゲットグループと ECS のセキュリティグループ(SG)の設定に不備があった。

## Decision Drivers (決定要因)

1. ALB のヘルスチェックは、**ターゲットグループに紐づくタスクが実際にリッスンしているポート・パス**に届く必要がある
2. ALB → ECS 間の通信はセキュリティグループで許可されている必要がある(ALB SG から ECS SG へのポート開放)
3. ヘルスチェックは HTTP 200 を返す軽量なエンドポイント(`/` や `/health`)に向けるべきで、認証や重い処理を伴うパスにしない

## Considered Options (検討した選択肢)

| 選択肢 | 評価 | 補足 |
|--------|------|------|
| **ヘルスチェック用にコンテナポートとパスを正しく整備 (採用)** | ◎ | ターゲットグループのポート/パスと SG を実アプリの待受設定に合わせる正攻法 |
| ヘルスチェックを `GET /` のまま妥協する | △ | フレームワークによっては `/` が重い・リダイレクトする場合があり、専用ヘルスエンドポイントの方が堅牢 |
| ヘルスチェック失敗時の unhealthy 閾値を緩めて誤魔化す | × | 根本原因(到達性)を解決しない。タスク停止ループが緩慢になるだけ |

## Decision Outcome (決定)

**ALB ターゲットグループのヘルスチェック設定を、各ターゲット(コンテナ)の実際のリッスンポートと正常応答パスに一致させる。**

- ALB と ECS タスク間で、必要なポート(8000 / 8001)をセキュリティグループで明示的に許可(ALB SG をソースに指定)
- ヘルスチェックパスは HTTP 200 を確実に返すエンドポイントに設定
- タスク定義の `containerPort` とターゲットグループの `port` の整合を Terraform で一元管理

## Consequences (結果)

**良い点**

- タスクの停止ループが解消され、デプロイのたびに安定してローリング更新される
- 「ALB から見た到達性」のチェックリスト(ポート・パス・SG)が明文化され、次回以降の切り分けが高速化した

**悪い点**

- ポートが 2 種類(8000/8001)ある構成では、ターゲットグループを複数管理する設定コストが残る

## 学び

`Task failed ELB health checks` は「ECS の問題」ではなく「ALB からタスクまでの HTTP 通信が成立していない」という **ネットワーク到達性の問題** である。切り分けは (1) コンテナは起動しているか → (2) コンテナ内でポートはリッスンしているか → (3) SG で ALB からの通信は許可されているか → (4) ヘルスチェックのパス・ポートは正しいか、の順に辿るのが定石。本件は [ADR-0002](0002-container-communication-endpoint-resolution.md)(localhost 問題)と並び、「どこまでの通信が届いているか」を層で切り分ける能力を鍛える経験となった。
