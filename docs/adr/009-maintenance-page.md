# 009. メンテナンス画面の表示方式の選定（ALB固定レスポンス vs Route 53 切り替え）

- **Status**: 採用 (Accepted) ※前提となる未整備項目あり
- **Date**: 2026-09-27
- **出典**: Session 02
- **Related**: `modules/alb/main.tf`（リスナー・リスナールール）/ `modules/vpc/main.tf`（ALB SG）/ `.github/workflows/destroy.yml` / `docs/review/ECS`（メモ）

## 背景

計画メンテナンス時に、**ユーザーには案内画面を表示しつつ、開発者（検証者）は通常どおりシステムへ到達できる**状態を作る必要があった。

検討対象は、**ALBの固定レスポンス（`fixed-response` アクション）** と、**Route 53 のレコード／ヘルスチェックを切り替える方式**である。判断に影響したのは次の3点である。

1. この基盤には **ドメインもホストゾーンも無い**（`route53` / `acm` の定義はリポジトリに0件）。現状のアクセスはALBのDNS名に対して行われている
2. ALBの本番リスナールールは **ECSのBlue/Greenが重みを書き換える**（`lifecycle { ignore_changes = [action] }`）ため、既存ルールのアクションを書き換える方式は成立しない
3. リポジトリのメモ（`docs/review/ECS`）に「WAFを使って開発者側はちゃんと見れる。ユーザーからは…」という検討記録が残っており、**閲覧者の属性で出し分けたい**という要求があった

## 検討した選択肢

| 選択肢 | 評価 | 補足 |
| --- | --- | --- |
| **ALBの固定レスポンス（採用）** | ◎ | ルールのアクションを `fixed-response`（503 + `text/html`）にすれば、バックエンドのタスク状態に関わらず案内画面を返せる。**追加リソース・追加課金・DNS変更が不要**で、ALBのDNS名のまま即時切替できる。既存ルールが `ignore_changes = [action]` を持つため、**優先度の高い新しいリスナールールとして追加**すれば、ECSによる重み操作と衝突しない |
| Route 53 の切り替え | △ | メンテナンス用の別オリジン（S3静的サイト等）へ切り替える方式は、アプリが完全に停止していても案内を出せる点で優れる。ただし**ホストゾーン（とドメイン）が前提**であり、現状は存在しない。Route 53 のホストゾーンは固定費が発生し、レコードのTTLによる切替遅延も受ける。かつ、ユーザーを別オリジンへ移す時点で**TLS証明書とオリジンの用意**がセットで必要になる |
| CloudFront を前段に置き、オリジン切替／カスタムエラーページで対応 | ○ | キャッシュとエラーページ制御が可能。ただし前段の追加は構成要素と固定費を増やし、本件の要件（案内画面の表示）に対しては過剰 |
| WAF でブロックし、固定の応答を返す | △ | WAFはブロック応答の本文を自由に設計できず、案内画面の用途には向かない。加えて WAF 自体が未導入 |
| アプリ側でメンテナンスフラグを実装 | × | タスクが停止している状態では動かない。**メンテナンス時にこそ動かない**方式は手段として成立しない |

## 決定

**メンテナンス画面は ALB の固定レスポンスで表示する。**

- 本番リスナー（1500 / 8000）に対して、**既存ルールより高い優先度の新しい `aws_lb_listener_rule` を追加**し、アクションを `fixed-response`（503 + `text/html`、必要に応じて `Retry-After`）にする
- 既存の本番リスナールールのアクションは書き換えない。**`lifecycle { ignore_changes = [action] }` が設定されているため、書き換えても Terraform は差分を適用せず、かつECSの重み操作と競合する**からである。この制約は、Blue/Green を採用した帰結（[ADR-012](./012-backend-deployment-strategy.md)）として受け入れる
- Route 53 は採用しない。理由は構成の重さではなく、**現時点でドメインとホストゾーンが存在せず、TLS証明書も未整備**であり、メンテナンス画面のために新たに外部公開の入口を用意することになるためである
- 開発者／検証者が通常どおり到達できるよう、メンテナンスルールには**除外条件**（`custom_header` または `source_ip`）を設ける。これにより「ユーザーには案内画面、開発者には実環境」という要求を、**同一ALB内で**満たす

### あわせて確認すべき制約

| 重大度 | 内容 | 対応 |
| --- | --- | --- |
| 高 | 固定レスポンスは**ALB自体が生きていることが前提**。ALBを含む全削除（`destroy.yml`）の間は案内を出せない | 全削除の間の案内は別レイヤ（Route 53／CloudFront）が必要になることを明示し、要件から切り離して扱う |
| 中 | 除外条件（`custom_header`）を秘匿値にすると、**その値が漏れれば回避できる** | 値は Secrets Manager 等で管理し、ローテーション可能にする |
| 中 | バックエンドのテストルールの条件が `path_pattern = ["api/*"]` であり、ALBのパスパターンとして**先頭 `/` が必要な形式**と整合しない可能性がある | `"/api/*"` に修正するか、本番ルールと同様 `"*"` に整理する |
| 中 | メンテナンス中もバックエンドのタスクを起動したままにするか、`desired_count` を落とすかが未定義 | 目的（DBメンテナンス等）に応じて運用手順に明記する。落とす場合は復旧手順とセットで定義する |

## 結果

**良い点**
- 追加リソース・追加課金・DNS変更なしで、**ルール1本の追加により即時に案内画面へ切り替えられる**
- タスクが全停止していても、コンテナイメージの更新中でも、ALBが応答するため案内が途切れない
- 除外条件により、**ユーザーには案内、開発者には実環境**という出し分けが同一ALB内で完結する
- ECSのBlue/Greenが管理する重み設定と衝突しない（新規ルールとして追加するため）

**悪い点・トレードオフ**
- **ALBより上流の障害（ALB自体の削除・障害）では案内を出せない**。Route 53／CloudFront を採らない以上、この範囲は原理的にカバーできない
- メンテナンス状態がTerraformのコード（ルールの有無）として表現されるため、**切替のたびに apply が必要**になる。手動で即時に切り替えたい運用とは相性が悪い
- 除外条件の秘匿値の管理という、新しい管理対象が増える
- 503を返すため、検索エンジンや監視からは「異常」として観測される。外形監視を導入する場合は、メンテナンス時間の扱い（監視の抑止）を決める必要がある

## 学び

メンテナンス画面は「停まっているときに何を見せるか」という要件だが、**方式の選択は上位レイヤの有無（ドメイン・DNS・証明書）に強く依存する**。Route 53 切り替えは一般には強力だが、ホストゾーンも証明書も無い現状では、まず入口を新設する作業から始めることになる。一方ALBの固定レスポンスは、既にある入口を使うため即時性とコストの両面で優位に立つ。

判断の分かれ目は「**どこまでを守るか**」である。ALBが生きている範囲のメンテナンスなら固定レスポンスで十分だが、ALB自体を消す作業をカバーしようとした瞬間に別レイヤが必要になる。要件の範囲を先に確定させることが、方式選定より重要だった。

また、既存のリスナールールに `ignore_changes = [action]` が入っているという**一見些細な設定が、メンテナンス画面の実装方式を制約する**という連鎖が生じた。Blue/Green の採用（[ADR-012](./012-backend-deployment-strategy.md)）が、ここで間接的に効いている。

## 未確認事項

- `fixed-response` を新しいリスナールールとして追加した場合に、ECSのBlue/Greenの切替と衝突しないかは実環境での確認が必要
- 除外条件を `custom_header` にした場合の実挙動（ブラウザからの検証手順を含む）は未検証
- `docs/review/ECS` のメモに「メンテナンス画面 ⇒ ALB固定レスポンス / Route53切り替え」との記載があるが、**採用理由の詳細はメモに残っていない**ため、決定過程は本ADRで再構成したものである
- メンテナンス中のタスク稼働方針（継続か停止か）は未定義
